> EXECUTION-TRACE CONTRACT
> ==================================================
> 
> Venkat has approved the following requirement.
> 
> Every meaningful workflow in the Chief of Staff OS must produce an inspectable execution trace.
> 
> The purpose is to make the process visible and auditable.
> 
> A user should be able to determine:
> 
> - what the workflow was trying to accomplish
> - what context it required
> - what context it actually loaded
> - where that context came from
> - which sources it checked
> - which significant tools/actions ran
> - which named stages executed
> - which stages did not execute
> - which decisions were made
> - which materially distinct alternatives were rejected
> - why those alternatives were rejected
> - what evidence supported material decisions
> - what assumptions or unknowns remained
> - what validations ran
> - which validations passed or failed
> - what output was created
> - where the output landed
> - which later workflow or state consumed it
> - whether the workflow completed according to its contract
> 
> 
> IMPORTANT DISTINCTION
> 
> An execution trace is NOT raw model chain-of-thought.
> 
> Do not design storage for hidden reasoning tokens or private model scratch work.
> 
> The durable trace records inspectable operational reasoning such as:
> 
> - decision
> - evidence used
> - materially relevant alternatives
> - selection rationale
> - confidence
> - uncertainty
> - source
> - action
> - validation
> - result
> 
> The system must remain auditable without depending on private chain-of-thought.
>

> ==================================================
> TRACE CONTRACT — APPROVED REQUIREMENTS
> ==================================================
> 
> TRACE-1 — SCOPE
> 
> Every meaningful workflow produces an execution trace.
> 
> Phase 5 must operationalize "meaningful workflow" sufficiently for later implementation.
> 
> At minimum test whether this includes workflows that:
> 
> - produce a durable artifact
> - modify persistent state
> - inform a consequential decision
> - prepare a decision for Venkat
> - consume or create governed context
> - interact with restricted/confidential information
> - prepare external communication
> - generate research or evidence
> - feed another governed workflow
> - evaluate, classify, rank, recommend, approve, reject, or defer material work
> 
> Do not require heavy trace machinery for trivial transient interactions if they do not meet the meaningful-workflow threshold.
> 
> Prefer proportional trace depth over separate tracing architectures.
> 
> 
> TRACE-2 — GRANULARITY
> 
> Trace:
> 
> - named workflow stages
> - significant tool actions
> - significant source reads
> - meaningful state writes
> - material decisions
> - validation steps
> - failure/recovery events
> 
> Do not record every microscopic operation.
> 
> 
> TRACE-3 — CONTEXT CONTRACT
> 
> Every meaningful workflow must define its required and optional context.
> 
> For each run, record:
> 
> REQUIRED CONTEXT
> - what the workflow needs in order to produce a trustworthy result
> 
> OPTIONAL CONTEXT
> - what improves the result but is not required
> 
> ACTUAL CONTEXT LOADED
> - source
> - version where applicable
> - hash where appropriate
> - compact snapshot or summary of the material context consumed
> 
> Prefer references over duplication.
> 
> Do not copy canonical truth into every trace.
> 
> Use:
> 
> source + version + hash + compact context snapshot
> 
> where practical.
> 
> 
> TRACE-4 — MISSING OR STALE CONTEXT
> 
> If required context is missing or materially stale:
> 
> BLOCK the workflow.
> 
> Do not silently continue and generate a polished result.
> 
> If optional context is missing or stale:
> 
> continue only if appropriate and produce a visible warning in the trace.
> 
> The distinction between required and optional context must be defined by the workflow contract rather than improvised after failure.
> 
> 
> TRACE-5 — MATERIAL ALTERNATIVES
> 
> Store materially distinct rejected alternatives when they affected a consequential choice.
> 
> For each retained alternative record:
> 
> - alternative
> - reason considered
> - reason rejected
> - evidence or constraint that drove rejection
> - reversal evidence where useful
> 
> Do not record every imaginable option.
> 
> 
> TRACE-6 — OUTPUT VISIBILITY
> 
> The user-facing deliverable should remain clean.
> 
> Do not dump the entire execution trace into:
> 
> - a call brief
> - daily brief
> - recommendation
> - research summary
> - email draft
> - public artifact
> 
> Instead, every governed user-facing output must provide a CLICKABLE LINK to the full stored execution trace.
> 
> The trace itself should provide reciprocal links to:
> 
> - the final output
> - material source artifacts
> - relevant decisions
> - relevant upstream traces when appropriate
> 
> Prefer repository-relative Markdown links or the repository's existing durable link convention so links remain usable and portable.
> 
> Do not satisfy this requirement with an opaque ID or plain path when the surrounding surface supports a clickable link.
> 
> 
> TRACE-7 — COMPLETION RULE
> 
> A governed workflow is NOT complete merely because its deliverable exists.
> 
> Completion requires:
> 
> 1. required deliverable exists
> 2. required execution trace exists
> 3. required validation checks have run
> 4. blocking checks passed
> 5. output links to the trace
> 6. trace links to the output
> 7. required landing/state updates occurred
> 
> If one of these required items is absent:
> 
> status is incomplete, blocked, or failed according to the workflow contract.
> 
> Never silently call the workflow done.
