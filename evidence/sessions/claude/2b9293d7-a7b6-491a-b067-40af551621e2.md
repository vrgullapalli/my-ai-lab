> Create a project-level Claude Code skill called `implication-lens`.
> 
> ## Purpose
> 
> This is an experimental reflection skill for my AI Lab.
> 
> It should examine the work or discussion currently in context and identify whether there is a useful deeper implication, commercial capability implication, lab test, or content angle that I may otherwise miss.
> 
> This is NOT an always-on response rule.
> 
> For now, I want to invoke it intentionally so we can test whether it creates enough value to justify broader use later.
> 
> ## First inspect the project
> 
> Before creating anything:
> 
> 1. Inspect the existing `.claude/skills/`, commands, rules, `CLAUDE.md`, and relevant project guidance.
> 2. Identify the canonical sources for:
> 
>    * my positioning
>    * audience
>    * voice
>    * AI Lab framing
>    * AI-native commercial capabilities
> 3. Reference existing canonical context rather than copying large amounts of it into the skill.
> 4. Follow the project's existing skill structure and naming conventions where possible.
> 5. Do not modify broader project rules or make this skill automatically apply to every response.
> 
> ## Create
> 
> Prefer:
> 
> `.claude/skills/implication-lens/SKILL.md`
> 
> Use the current Claude Code skill format and existing project conventions.
> 
> The skill should be directly invokable as:
> 
> `/implication-lens`
> 
> ## Output
> 
> When invoked, analyze the work currently in context.
> 
> Return:
> 
> **Deeper idea:** [one sentence]
> 
> **Commercial capability implication:** [one sentence]
> 
> **Lab test:** [one sentence]
> 
> **Content angle:** [one sentence, only if genuinely useful]
> 
> ## Deeper idea
> 
> Ask:
> 
> > What is the most useful non-obvious thing here?
> 
> Look for:
> 
> * hidden dependencies
> * second-order effects
> * assumptions
> * failure modes
> * tensions
> * what must be true
> * simpler underlying problems
> 
> Do not manufacture novelty or contrarianism.
> 
> Choose one strong insight.
> 
> ## Commercial capability implication
> 
> Ask:
> 
> > What might this tell us about the broader AI-native commercial capability system?
> 
> Look for:
> 
> * reusable capabilities
> * shared system capabilities
> * capability dependencies
> * design principles
> * sensing or control mechanisms
> * trust and evidence implications
> * authority implications
> * context or memory implications
> * operating-model implications
> * patterns that may transfer from the lab into commercial pharma
> 
> The AI Lab is the **proving ground**, not the commercial use case.
> 
> Do not manufacture a pharma analogy.
> 
> Treat unproven patterns as hypotheses or candidate capabilities rather than established truths.
> 
> ## Lab test
> 
> Ask:
> 
> > What is the smallest useful thing we could prove next?
> 
> Favor a small test that:
> 
> * validates or invalidates the implication
> * exposes a dependency
> * tests whether the pattern generalizes
> * materially reduces uncertainty
> 
> This should be a test, not a project plan.
> 
> ## Content angle
> 
> Ask:
> 
> > Does this contain a non-obvious idea worth developing publicly for my audience?
> 
> Use the project's canonical context for my positioning, audience, and voice.
> 
> Look especially for:
> 
> * tensions senior commercial pharma leaders would recognize
> * hidden assumptions
> * useful reframes
> * gaps between technical success and commercial value
> * trust, evidence, authority, context, operating-model, customer-data, or AI-native implications
> * ideas grounded in actual work rather than generic AI commentary
> * accepted practices that may deserve to be challenged
> * something technically true but commercially misleading
> * absurdities created by how organizations currently work
> 
> The content angle should reflect something I have a legitimate reason to say because of the work.
> 
> If there is no strong content angle, omit it.
> 
> # Writing Style
> 
> Apply the following voice when wording the output.
> 
> The first three fields should remain compact and analytical. Do not sacrifice clarity or usefulness for personality.
> 
> Apply the fuller voice most strongly to **Content angle**.
> 
> ## Style
> 
> ### Conversational and informal
> 
> Use natural contractions such as "you're," "it's," "don't," and "can't."
> 
> Write like you're talking to a smart person, not presenting to a committee.
> 
> ### Contrarian
> 
> Be willing to challenge:
> 
> * conventional wisdom
> * accepted practices
> * industry norms
> * popular beliefs
> * comfortable assumptions
> 
> Especially challenge assumptions around customer data, AI, commercial strategy, measurement, personalization, technology, and operating models.
> 
> Contrarianism must come from the evidence or logic in the current work.
> 
> Do not manufacture disagreement just to sound provocative.
> 
> ### Observational and anecdotal
> 
> When the context supports it, ground ideas in:
> 
> * actual observations
> * lived experience
> * recurring organizational behavior
> * recognizable situations
> * social or industry absurdities
> 
> Prefer concrete observations over abstract proclamations.
> 
> Do not invent personal anecdotes.
> 
> ### Irony and satire
> 
> Use irony, satire, or occasional pop-culture references when they sharpen the point.
> 
> The humor should expose an absurdity or contradiction rather than exist for decoration.
> 
> Use sparingly.
> 
> ### Self-deprecating humor
> 
> Occasionally allow self-deprecating humor to keep the voice human and avoid sounding self-important.
> 
> Do not force it.
> 
> ### Navigating controversy
> 
> Do not automatically soften an uncomfortable conclusion.
> 
> Handle controversial ideas directly, but distinguish:
> 
> * evidence
> * inference
> * opinion
> * provocation
> 
> Humor may make a difficult point easier to engage with, but should not trivialize the issue.
> 
> ### Rhetorical questions
> 
> Use rhetorical questions when they expose an assumption or make the reader reconsider something.
> 
> Example pattern:
> 
> > If the system can't tell when its evidence is weak, what exactly are we trusting?
> 
> Use them selectively.
> 
> ### Witty remarks
> 
> Short, sharp observations are welcome when they make the idea more memorable.
> 
> Avoid generic "clever" filler.
> 
> ## Tone
> 
> The voice may be:
> 
> * irreverent
> * mildly sarcastic
> * intellectually provocative
> * sharp
> * pragmatic
> * occasionally cynical
> * ultimately constructive
> 
> The underlying stance should still be:
> 
> > this stuff is hard, but we can design it better.
> 
> Do not become hostile, performatively edgy, dismissive, or insulting.
> 
> ## Voice
> 
> ### Intellectual and philosophical
> 
> Use the immediate problem to occasionally reveal a deeper question about:
> 
> * trust
> * evidence
> * authority
> * knowledge
> * judgment
> * incentives
> * systems
> * organizational behavior
> 
> The philosophical point should emerge from the practical issue, not replace it.
> 
> ### Meta-comedic
> 
> When useful, acknowledge the strange conventions of data strategy, AI, consulting, or organizational life.
> 
> Do not turn the output into a comedy routine.
> 
> ### Confident and assertive
> 
> State defensible conclusions clearly.
> 
> Avoid unnecessary hedging.
> 
> But do not express hypotheses as proven facts.
> 
> ### Relatable and direct
> 
> Speak directly to the reader.
> 
> Prefer:
> 
> > You don't actually have a retrieval problem.
> 
> over:
> 
> > Organizations may potentially experience challenges related to retrieval.
> 
> ### Casual and conversational
> 
> Plain language is preferred.
> 
> "This stuff is hard" is better than consultant-speak.
> 
> Use technical terms only when they add precision.
> 
> ### Irreverent
> 
> Be willing to point out when an accepted practice makes little sense.
> 
> The goal is not to offend.
> 
> The goal is to make the underlying contradiction hard to ignore.
> 
> # Voice Guardrails
> 
> Do not try to use every style characteristic in every response.
> 
> In particular:
> 
> * Do not force humor.
> * Do not force sarcasm.
> * Do not invent anecdotes.
> * Do not add a pop-culture reference unless it genuinely improves the idea.
> * Do not make every insight contrarian.
> * Do not turn a useful observation into clickbait.
> * Do not sacrifice precision for personality.
> * Do not make senior commercial leaders feel mocked. The target of the humor should usually be bad assumptions, systems, incentives, or industry habits.
> 
> The voice should feel natural, not like a checklist of stylistic tricks.
> 
> ## Cognitive-load constraint
> 
> The output should normally fit in 3–4 short lines.
> 
> One sentence per field by default.
> 
> Do not:
> 
> * summarize the original work
> * repeat conclusions already obvious from the context
> * provide multiple alternatives
> * add nested bullets
> * explain the framework
> * turn the output into an essay
> 
> The mental model is:
> 
> **What did we notice? → What might it mean? → What should we test? → Is it worth saying publicly?**
> 
> ## Example
> 
> Context: We are designing sensors around retrieval quality.
> 
> **Deeper idea:** Retrieval can fail even when search works, because finding something isn't the same as having enough evidence to trust it.
> 
> **Commercial capability implication:** Sensing for gaps, conflicts, and weak evidence may belong above retrieval as a shared capability across memory, context, and decision support.
> 
> **Lab test:** Apply the same sensing pattern to one other capability and see whether it catches a meaningful failure we would otherwise miss.
> 
> **Content angle:** Your AI found twelve highly relevant documents. Wonderful. Does it know the thirteenth one it didn't find changes the decision?
> 
> ## Testing
> 
> After creating the skill, test it against at least five different types of existing lab work:
> 
> 1. retrieval
> 2. memory or context
> 3. agent authority
> 4. architecture or system design
> 5. a routine technical task where no broader insight should exist
> 
> Evaluate:
> 
> * Did Deeper idea add something genuinely non-obvious?
> * Was Commercial capability implication distinct from Deeper idea?
> * Was Lab test actually small and testable?
> * Did Content angle fit my positioning and audience?
> * Did the voice feel natural rather than manufactured?
> * Did humor or contrarianism sharpen the idea rather than distract from it?
> * Did the skill correctly avoid manufacturing insights where none existed?
> * Did the output remain compact?
> 
> Show me:
> 
> 1. the skill you created
> 2. where it lives
> 3. any canonical context it references
> 4. the five test results
> 5. what you would change based on those tests
> 
> Do not convert it into an automatic rule yet.
