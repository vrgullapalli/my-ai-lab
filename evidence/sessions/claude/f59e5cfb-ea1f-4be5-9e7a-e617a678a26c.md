## 5. Duplication and conflict risks

**C-1 — Sequencing conflict (the blocker).** D-119(c) requires P6-02…P6-12 before further normal OS build or audit work. This slice is normal OS build work under the plain reading. *Confidence: High. Counterargument: money-work exemption. Reverses on: his ruling.*

**C-2 — Public-experience conflict.** D-014 keeps the first public experience undecided; D-007 puts private use first; D-108 gates the content engine on the Private MVP, which is not done. The slice proposes a subscriber-facing product with saved results. *Confidence: High.*

**C-3 — The evidence record already argues against a standing discovery outcome.** `P25-N02` is the register's "strongest negative control"; `P25-O17` survives only as a Provided hypothesis awaiting 2–3 bounded tests. Building the full nine-part slice would skip those tests. *Confidence: High. Counterargument: the register itself names bounded tests as the path, so a **small** test is canon-consistent — a **product** is not.*

**C-4 — "Public product" is an overloaded term.** In [DONE.md](DONE.md) it means open-sourcing the OS as a customizable template with private data stripped. The proposal means a reader-facing decision instrument. These share a name and nothing else. Left unresolved, a gate written for one will be read as covering the other. *Confidence: High.*

**C-5 — Decision Problem as central object vs D-009.** Making the Decision Problem the organizing object creates a new record type that overlaps `DECISIONS.md`, `state/projects/`, `state/open-loops.md`, and the seeds graph. D-009 prohibits competing parallel trackers. *Confidence: Medium-High — it depends entirely on whether the Decision Problem holds *reader* problems (no overlap) or *his* decisions (direct overlap).*

**C-6 — Article-centred vs problem-centred content model.** The repo's whole content chain today is article-centred: [content/](content/), the seeds corpus, the content brief/spec pair, D-110's "publish first." The frozen spec `content-spec--nba-context--v1.md` is a *document* specification. Re-centring on Decision Problems would orphan or require re-keying that work. *Confidence: Medium.*

**C-7 — Private evidence powering public claims.** Every number in the slice would trace back to `nba-evidence-register-v1.csv`, the NBA reconstruction, and interview records containing employer-identifiable material (loop #14, G-8/G-9). Today's fences are gitignore plus convention. Publishing changes the failure mode from "wrong file committed" to "confidential detail published." *Confidence: High. This is the risk I would rank first on consequence.*

**C-8 — Retention rule inversion.** The no-delete/archive-only rule is a **Critical** global rule. A subscriber product with saved results needs real deletion. These cannot both apply to the same tree. *Confidence: High.*

**C-9 — Correction ownership.** D-116 makes his intervention count a health measure and makes anything he catches an assurance incident. A public instrument that returns wrong recommendations creates outside-facing incidents with no owner, because `state/assurance/` does not exist yet (P6-05). *Confidence: High.*

**C-10 — Positioning is not settled.** D-121 records Layer 3 (buyer and offer) as **open**, pending Gate 2 market evidence. A public instrument asserts a buyer. *Confidence: High.*

**C-11 — Governance of this appraisal itself.** Hard rule 16 requires a written, approved, traceable plan for "any research or analysis." No plan for this appraisal exists in `plans/`. I am surfacing this rather than fixing it (hard rule 7). *Confidence: High. Counterargument: hard rule 13 — a question is a question, answer it. The two rules meet here and only Venkat can resolve which governs a commissioned read-only appraisal.*

### Strongest counterargument to placing the slice inside the Chief of Staff OS repository

**This repository's entire value is that it is a private, append-only evidence record whose integrity depends on nothing inside it ever facing outward.**

Its governing invariants are private-first (D-007), never-delete, one-home-per-fact (D-009), publication-is-human-only (D-012), and evidence-before-claim (ROOT.md "Earned Trust"). A subscriber product needs the opposite on at least four of those: it deletes user data on request, it keeps a second store of reader-owned records, it serves output without a human in the loop for each response, and it exposes derived claims whose sources are confidential.

Putting it here does not add a folder. It puts a public attack surface — and someone else's personal data — inside the one place that currently holds his unredacted client history, his employer-named work inventory, and his positioning evidence. The repo has no remote, no CI, no tests, and no auth model. Its safety today is *obscurity plus discipline*, and a public product removes the first half.

*What would weaken this counterargument:* if Release 0 is genuinely paper-only — a classification model, a worked example, a result contract as a written schema, and a low-fidelity walkthrough — then nothing faces outward and the counterargument does not bite. It bites the moment anything is served.
