> **The problem the naive version creates.** Hard rule 2 says DECISIONS.md
> entries change only by "an appended supersession that names what it replaces."
> The obvious hook — block every edit, allow only appends at end of file — would
> have blocked the one real supersession this repo has performed. D-101 was
> amended by a `>` blockquote inserted **inside** the entry, at lines 128–134.
> 
> **The correct test.** An edit is legal when the new text preserves the old text
> whole and only adds to it:
> 
> ```python
> # .claude/hooks/decisions-append-only.py — the load-bearing three lines
> old = tool_input.get("old_string", "")
> new = tool_input.get("new_string", "")
> is_append_only = old in new          # old survives verbatim inside new
> ```
> 
> This permits D-101's inline blockquote (the entry text is untouched, new lines
> are added around it) and blocks any rewrite or deletion.
> 
> **Why hookify cannot do this.** Hookify rules match one field against one
> pattern. Comparing `old_string` to `new_string` is a two-field comparison, so
> this one needs a real script. Hooks 3 is different — see below.
> 
> **Config**, in a new `.claude/settings.json`:
> 
> ```json
> {
>   "hooks": {
>     "PreToolUse": [
>       {
>         "matcher": "Edit|Write",
>         "hooks": [
>           { "type": "command",
>             "command": "python3 \"$CLAUDE_PROJECT_DIR/.claude/hooks/decisions-append-only.py\"",
>             "timeout": 10 }
>         ]
>       }
>     ]
>   }
> }
> ```
> 
> **Blocking**, using the documented schema:
> 
> ```json
> { "hookSpecificOutput": {
>     "hookEventName": "PreToolUse",
>     "permissionDecision": "deny",
>     "permissionDecisionReason": "DECISIONS.md is append-only (hard rule 2). This edit removes or rewrites existing text. Add a supersession that names what it replaces." } }
> ```
> 
> **Dependencies:** the two entry formats must be reconciled first. D-001–017 use
> `**D-002** · statement · active · date`; D-101–111 use `**D-101** · ACTIVE ·
> statement`. A guard is fine with both, but a supersession *convention* is not.
> 
> **How to prove it works** — the repo's own bar is "proven by attempting the
> violation." Three test edits: rewrite a D-002 clause (must block), append a new
> entry at end of file (must pass), insert a blockquote amendment inside D-101
> exactly as the real one is written (must pass).
> 
> ### 2. Receipt-on-stop hook
> 
> **Correction to the report's rationale.** Loop #19 has two failures in it. The
> overwrite half is already fixed — receipts now carry HHMM (`2026-08-14-1633.md`).
> The omission half is not: sessions can still end with no receipt. Only the
> second half justifies this hook.
> 
> **The weak proxy problem.** A Stop hook can cheaply check "does a receipt exist
> dated today." That passes on a stale morning receipt even if tonight's session
> wrote nothing. The stronger check is git-based:
> 
> ```bash
> # fires only if the session changed tracked files but wrote no receipt
> CHANGED=$(git -C "$CLAUDE_PROJECT_DIR" status --porcelain | grep -c .)
> RECEIPT=$(git -C "$CLAUDE_PROJECT_DIR" status --porcelain state/receipts/ | grep -c .)
> [ "$CHANGED" -gt 0 ] && [ "$RECEIPT" -eq 0 ] && echo BLOCK
> ```
> 
> **The infinite-loop guard is mandatory.** Read `stop_hook_active` from stdin and
> exit 0 immediately if true, or the hook fires forever. Claude Code overrides
> after 8 consecutive blocks, but relying on that is a bug, not a design.
> 
> ```json
> { "hookSpecificOutput": {
>     "hookEventName": "Stop",
>     "decision": "block",
>     "reason": "Files changed this session but no receipt was written. Run the session-receipt skill." } }
> ```
> 
> **Key consideration, and the reason this is deferred:** it will nag on trivial
> sessions. Hard rule 13 says a question is a question — a session where Venkat
> asked something and got an answer should not demand a receipt. Any build needs
> a cheap exemption for read-only sessions.
> 
> ### 3. Nested-CLAUDE.md guard
> 
> **The one hookify can express**, because it is a single field against a single
> pattern. Write `.claude/hookify.nested-claude-md.local.md`:
> 
> ```markdown
> ---
> name: nested-claude-md-guard
> enabled: true
> event: file
> action: block
> conditions:
>   - field: file_path
>     operator: regex_match
>     pattern: chief-of-staff/.+/CLAUDE\.md$
> ---
> 
> **A second CLAUDE.md is a competing operating contract (D-009).**
> 
> One duplicate auto-loaded on 2026-08-11 and had to be archived. The root
> `CLAUDE.md` is the only one. Put project rules in `.claude/rules/` instead.
> ```
> 
> The regex matches any path with a directory between the repo root and
> `CLAUDE.md`, so the root file itself is never blocked.
> 
> **Dependency:** none. This is the cheapest of the three and could be built
> alone. PLAN.md bundles it with hooks 1 and 2 as "first three hooks," which is a
> convenience, not a technical requirement — worth splitting when the queue is
> next reordered.
> 
> **Add `.claude/*.local.md` to `.gitignore`** if hookify is used, per its own
> convention.
