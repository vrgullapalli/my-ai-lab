> ## 1. INGESTION / CONNECTOR PATTERNS
> 
> **Folder-watcher + multi-source funnel (most common pattern).**
> - `minutes` (silverstein/minutes, MIT, github.com/silverstein/minutes) — Accepts audio from desktop mic, phone voice memos synced via iCloud/Dropbox/Google Drive, Zoom/Meet/Teams calls, and existing transcripts from other tools. Watcher "settles for 2 seconds before processing" to let cloud sync finish writing the file — a specific fix for the classic "half-written file ingested" bug. Includes a dedicated Granola importer that skips already-processed meetings. Observed (fetched README).
> - `obsidian-vox` (vincentbavitz/obsidian-vox, MIT) — Watches a directory (default `Voice/unprocessed`); on new file, sends to a self-hosted Docker backend running Whisper. Naming convention (`R{1-5}{category} {title}`) is itself an ingestion-time classification signal set by the user at capture time, not inferred later. Observed.

> - `OpenTranscribe` (attevon-llc/OpenTranscribe, AGPL-3.0) — Multi-source watchers (folder, S3, SMB) feeding one transcription pipeline (WhisperX/faster-whisper + PyAnnote v4 diarization). Observed.

> - **`notesGPT`** (Nutlope/notesGPT, MIT-ish OSS, DEV Community writeup by creator) — Simpler pipeline: record → Whisper transcription → Mixtral (via Together AI, JSON mode) extracts action items → displayed in an action-items view; embeddings via Together AI power search. Convex backend. Observed (creator's own writeup + repo).

This is a meaningfully different design choice from `minutes`/`notesGPT`: **push classification burden to the user at capture time** vs. **infer it after the fact**. Observed.
> - **`Cognee`**'s "Cognify" stage does LLM-based entity/relationship extraction with "cognitive-science-grounded ontology generation," using typed Pydantic schemas to declare what counts as an extractable object — i.e., classification-by-schema rather than free classification. > ## 5. CROSS-NOTE / LONGITUDINAL REASONING PATTERNS (the core question)
> 
> This is the least mature area of the OSS landscape surveyed. Findings, roughly strongest-to-weakest evidence:
> 
> - **GraphRAG community detection** (Microsoft GraphRAG, graphrag.com docs) — closest generic mechanism for "you returned to this theme repeatedly." Uses the Leiden algorithm hierarchically on the extracted entity/relationship graph to find densely-connected communities at multiple levels (high-level theme → low-level topic), then LLM-summarizes each community. This gives you "what are the recurring clusters in my corpus" as a batch/offline operation, not an online "you just touched this again" alert. Observed (docs), general-purpose text tool, not personal-capture-specific.
> - **Graphiti's bi-temporal model** (getzep/graphiti) is the only tool found that natively timestamps *when a fact became true* vs. *when the system learned it*, and preserves invalidated-not-deleted history — this is the substrate longitudinal pattern detection would be built on (you could query "what did I believe about X at each point in time" and diff it), but Graphiti itself does not ship a "recurring theme across N weeks" detector on top of that substrate. It's an enabling primitive, not the mechanism itself. Observed.
> - **Practitioner-built cross-session pattern detection** (Vikas Sah, Medium, "Your AI Agent Is a Goldfish," 2026-05-17) is the single most concrete mechanism found for the exact question asked: a weekly background job scans a **14-day episodic window** and extracts a pattern **only if it repeats across 3+ events with explicit causal reasoning attached** — an intentional threshold to suppress single-occurrence noise. This is a hand-built practitioner pattern, not a maintained OSS repo, but it's a directly answerable mechanism: *recurrence count + time window + causal-linkage requirement, gated before promotion*. He also reports this exact mechanism caught two bad over-generalizations from loosely related events in one month of real use, i.e., it still has a false-positive rate worth guarding against with a gate. Observed (practitioner blog, primary self-report, not independently verified).
> - **Mem0 v3 abandoned its graph layer** for personal-memory entity linking, replacing it with spaCy-based entity extraction + co-retrieval via entity-overlap combined with semantic + BM25 scoring — i.e., Mem0's answer to "related facts across time" is retrieval-time co-occurrence, not a standing cross-note pattern detector. Per the practitioner comparison (codepointer.dev, 2026-05-28), Mem0's own internal benchmarking found the graph variant "rarely justified its cost" — 3x slower, 2x the tokens, for marginal gains — a direct, named failure/tradeoff finding on graph-based longitudinal reasoning specifically. Observed.
> - No maintained OSS repo found that does temporal-burst/topic-recurrence detection purpose-built for personal notes (searched directly for "temporal topic burst detection," "resurfacing themes," "zettelkasten + spaced repetition + AI" — results were either generic topic-modeling repos (LDA/k-means, not personal-note-specific) or spaced-repetition tools that resurface by a scheduling algorithm (FSRS), not by detecting emergent recurrence. Unknown/gap — this appears to be a genuinely underbuilt area in OSS.
> 
> **Bottom line on this mechanism, stated directly:** the field has the *storage substrate* for longitudinal reasoning (Graphiti's bi-temporal graph, GraphRAG's hierarchical communities) but not a maintained, purpose-built "you keep coming back to this" detector for personal capture. The one concrete, working mechanism found (Sah's 14-day-window / 3+-occurrence / causal-link-required gate) is a single practitioner's hand-built job, not a library — it is a design to copy, not a dependency to install.

> ## 6. ROUTING PATTERNS
> 
> - **`minutes`**: routes by clip length (&gt;2min → meeting pipeline; &lt;2min → fast memo pipeline) and by explicit "policy-safe" profiles that gate which meetings authorized agent access downstream. Storage-as-routing: files land in `~/meetings/`, optionally symlinked/copied/direct-written into an Obsidian or Logseq vault — i.e., the destination system is treated as a sync target, not a separate write path. Observed.
> - **`khoj`** (khoj-ai/khoj, docs.khoj.dev) — "Automations" feature schedules repeated jobs (e.g., recurring research/summarization) that route output to email on a cron-like schedule in the user's local timezone; separately, a "routing" layer in the chat interface picks between response strategies. This is task-routing/scheduling, not content-classification-based routing to different destination systems. Observed (docs).
> - **`screenpipe`**: "pipes" are markdown files (prompt + schedule) that are effectively user-authored routing rules — each pipe queries the captured data store and independently decides what to do with matches (call an API, write a file). This appears to be assembled ad hoc in every "AI chief of staff" repo found (see below), not solved as a reusable component.

> ## 7. MEMORY-PROMOTION / LEARNING-FROM-CORRECTIONS PATTERNS
> 
> - **Mem0's ADD/UPDATE/DELETE/NOOP mechanism** (docs.mem0.ai, multiple secondary sources cross-checked): on ingesting a new candidate fact, Mem0 retrieves semantically similar existing memories via vector search, presents both to an LLM, and the LLM chooses one of four operations. Notably: **DELETE fires only on explicit contradiction, not on every new utterance** — a specific anti-thrash design decision. As of April 2026 Mem0 also shipped a "single-pass ADD-only" extraction mode (one LLM call instead of multiple UPDATE/DELETE cycles) claimed to improve LoCoMo benchmark scores by +20 points — i.e., they moved *away* from update-heavy operation toward simpler append-and-let-retrieval-rank, which is itself a lesson (complexity in the write path didn't pay for itself). Observed (mem0.ai blog + docs + practitioner secondary sources).
> - **Named failure mode with primary-source evidence**: "Getting Better at Working With You" (arXiv:2606.13174, Zhou et al., submitted 2026-06-11) directly measured that Mem0-based correction storage still leaves **57.5% of applicable preference/correction checks violated** in later sessions — i.e., "remembering" a correction (storing it as a fact) does not reliably mean "enforcing" it later. Their fix, **TRACE**: mine corrections from chat → rewrite as atomic, precise rules → compile into **runtime checks that must pass before the agent completes a task** (not passive retrieval-time recall). Reported results: violation rate on coding tasks dropped from 100.0% to 37.6% (familiar scenarios) / 2.0% (novel scenarios) after applying TRACE; memory-intensive task violations dropped from 100.0% to 60.5%. This is the strongest, most directly load-bearing finding in this research for the "learning from user corrections" mechanism: **passive memory storage of a correction is not the same as enforcement, and enforcement needs an explicit runtime-check compilation step, not just retrieval.** Observed (arXiv paper, primary source).
> - **Staged/gated promotion pattern** (Vikas Sah, Medium, 2026-05-17): consolidation writes to a *staging* memory tier (`type: semantic-candidate`), an eval suite (gold-set of ~20 real questions pulled from past conversations) runs against the candidate, and only passing candidates get promoted to live memory — explicitly modeled as "not auto-merge." He reports this staged-eval-gate approach caught 2 bad over-generalized reflections in one month of actual use. This is a direct, concrete answer to "how do you learn from corrections/consolidation without silent drift" — gate promotion behind an automated regression check against real historical Q&amp;A, don't let consolidation write straight to the memory the agent reads from. Observed (practitioner primary self-report).
> - **Graphiti/temporal invalidation** as a correction mechanism: contradicted facts get their validity window closed (`t_invalid` set) rather than being deleted or silently overwritten — so a "correction" is structurally a new edge plus an invalidation timestamp on the old one, preserving the fact that a correction happened and when. Observed.

> ## 8. FAILURE MODES PRACTITIONERS REPORT
> 
> 1. **Silent memory drift / propagation of wrong learnings** (Vikas Sah, Medium, 2026-05-17): "the most dangerous failure mode in 2026 isn't agents that forget, but agents that 'learn' the wrong thing and propagate it for weeks before anyone notices." Concrete example given: a killed idea's rationale never persisted to durable storage (write failure) *and* nothing retrieved it later (read failure) — a double failure, and the agent re-pitched the killed idea 11 days later. This is a directly relevant lesson for any classify-and-route system: **both write path and read path need to independently fail loudly, because a silent failure in either one produces the same symptom (system forgets a decision) but needs a different fix.**
> 
> 2. **Correction ≠ enforcement** (Zhou et al., arXiv 2606.13174, 2026-06-11): storing a correction as a retrievable memory fact does not reliably prevent recurrence of the same mistake — measured at 57.5% violation rate on Mem0 specifically. The fix required compiling corrections into hard runtime checks, not just adding them to a retrievable memory store. This directly challenges an assumption a capture-to-action system might make — that "log the correction to state/ or memory/" is sufficient; per this paper, it is not, without a checking step at the point of the next relevant action.
> 
> 3. **Context bleed / cross-domain contamination** (cognitivx.io, 2026-06-14, and independently corroborated by a Medium piece on AI-memory Chrome extensions): information learned in one context inappropriately surfaces in an unrelated one — the cited example is a health detail leaking into dietary advice, and separately a user reporting personal details ("coffee preferences") getting attached to a work conversation about a database schema. Named root cause: memory retrieval/classification failing to maintain proper boundaries between domains — directly relevant to a system that must separate content destined for a content pipeline vs. a private task tracker vs. a shared brief. cognitivx.io also names a **"personalization-convenience paradox"** (CHI 2026 study cited, not independently verified by this research): the feature users value most — background learning — is the one they can least audit or correct, creating an accountability gap between "the system got smarter" and "the user can see/undo what it learned."
> 
> 4. **Graph overhead not justified by benefit, in practice** (Mem0's own benchmarking, reported via codepointer.dev practitioner comparison, 2026-05-28): Mem0's team found their own optional graph layer ran 3x slower and used 2x the tokens for marginal quality gain, and removed it from the v3 default path in favor of simpler entity linking. Direct practitioner lesson: graph-structured memory has a real cost that should be justified by a specific downstream need (temporal/historical queries, multi-hop traversal), not adopted by default — echoed by the same author's explicit framing: "the real question is whether reads need traversal and whether writes need history," and complexity should only be added where that's true.
> 
> 5. **Product churn / consolidation risk in the OSS meeting-notetaker space**: the shutdown of Rewind/Limitless following Meta's December 2025 acquisition (multiple corroborating sources: winbuzzer.com, 9to5mac.com, p4sc4l.substack.com, all 2025-12) is the most consequential cautionary data point found — a privacy-positioned, well-funded lifelogging product with real usage was killed within weeks of acquisition, and non-US/EU users reportedly had their data deleted on a hard deadline (Dec 19, 2025). Lesson for anyone building a personal capture-to-action system: **local-first storage in plain, portable formats (markdown, SQLite) is not a nice-to-have but the only mitigation against exactly this failure mode** — which is precisely the design choice `minutes`, `obsidian-vox`, `screenpipe`, and `Reor` all independently converged on ("ten years from now, grep still works on your corpus" — minutes README, directly on point).
>

> 
> ## 5 MOST TRANSFERABLE MECHANISMS OVERALL
> 
> 1. **Per-capture-type extraction templates, not one universal classifier** (`minutes`): select the structured-output schema (meeting / standup / 1-on-1 / voice-memo) based on capture source/length *before* running extraction, rather than asking one classifier to do everything. Closest direct match to the "classify into tasks/ideas/commitments/questions/content-seeds" requirement in the research question.
> 
> 2. **Storage location as the router**: write classified output directly into the destination system's own file/folder (vault path, task-tracker file) rather than building a separate dispatch/queue layer — reduces one whole category of failure (routing logic diverging from where things actually need to live).
> 
> 3. **Three-tier fingerprint dedup (within-source / cross-source / against-library)** (`OpenTranscribe`): a simple, directly implementable dedup design for a multi-tool ingestion pipeline where the same voice note might sync via two different paths.
> 
> 4. **Correction-to-runtime-check compilation, not just correction-to-memory-storage** (TRACE / arXiv:2606.13174): the single most important mechanism for "learning from user corrections" — a correction must be compiled into something checked at the next relevant decision point, not merely stored as a retrievable fact, or it will be violated roughly half the time.
> 
> 5. **Staged consolidation with an eval gate before promotion to live memory** (Sah, practitioner pattern): run pattern/theme detection into a *candidate* tier, validate against a small gold-set of real historical Q&amp;A, and only promote what passes — directly transferable as the mechanism for safely automating the "recurring theme across weeks" detection this research question cares about most, without risking silent drift.
> 
> ## 3 MOST COMMON FAILURE MODES
> 
> 1. **Passive storage mistaken for enforcement** — corrections/decisions get logged but nothing re-checks them at the moment they'd matter again (measured: 57.5% violation rate on Mem0; anecdotal: an 11-day-old killed idea resurfaced).
> 
> 2. **Silent drift from unvalidated consolidation** — background jobs that summarize/generalize across sessions and write straight to memory the agent reads from will occasionally over-generalize from weakly related events, and without a validation gate this goes unnoticed for weeks.
> 
> 3. **Cross-domain / cross-context bleed** — classification or retrieval fails to keep boundaries between contexts (personal vs. work, one project vs. another), causing irrelevant or inappropriate information to surface in the wrong destination.</result>
